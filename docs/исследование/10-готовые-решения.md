## Главное

1. **Ядро продукта №1 берём готовым.** `quran-muaalem` 0.3.0 (QML-1.0) уже содержит сервер:
   - экстра `[engine]`: FastAPI + LitServe, GPU ~1,5 ГБ, батчинг;
   - эндпоинт `/correct-recitation` возвращает JSON ошибок: позиция в усмани-тексте, тип ошибки, ожидаемая и фактическая длина мадда, название правила.

   Наша работа — только перевести этот JSON в объяснение на казахском и русском [факт, [PyPI](https://pypi.org/project/quran-muaalem/), [README](https://github.com/obadx/quran-muaalem)].

   *Пометка 18.11.2026 (проверено по пакету 0.3.0): готовые процессы `engine` и `app` в проде не используем — модель берём как библиотеку в свой речевой сервис, см. §1.2.*
2. **Новое по сравнению с документами 02 и 03 — пять находок:**
   - **TajweedFormer V4 от Quran Lab:** потоковая проверка на устройстве, SDK для Android, iOS, web и C, отклик каждые 160–320 мс. Лицензия NPL-1.2: бесплатно, но без платных функций и с «share-alike» (производные — только под той же лицензией).
   - **`quranic-phonemizer`** (MIT): правило таджвида на каждой букве, включая тафхим/таркик. Закрывает пробелы `cpfair`.
   - **Шрифт DigitalKhatt Madina** (OFL-1.1, © в том числе Tarteel) и MIT-демо отрисовки мусхафа на React Native Skia. Это юридически чистый шрифт мусхафа.
   - **У ДУМК есть открытый API расписания намаза** (годовая таблица по координатам).
   - **Две библиотеки, которые нельзя брать:** Notifee больше не поддерживается, а `react-native-track-player` v5 стал коммерческим.
3. **Слой слов и хифза.** Зрелого открытого Apache/MIT-движка «как Tarteel» нет. Лучшие готовые потоковые модели для устройства — Quran Lab (NPL-1.2). Коммерчески чистые кандидаты:
   - `Abdou/quran-asr-tiny` — лицензия не указана;
   - FastConformer-ar от NVIDIA — CC-BY-4.0, источники расходятся;
   - HisnLabs tajweed-v2 — Apache-2.0, офлайн-CTC.

   Серверный вердикт собираем из готового: muaalem + `quran-transcript` (MIT; в нём есть нечёткий фонетический поиск по всему Корану) + `Waqar144` (муташабихат, CC0).
4. **Мобильный стек — React Native + Expo.** Последние версии на npm: `expo` 58.0.26 (17.11.2026) и `react-native` 0.88.1 (27.10.2026) [факт, [npm expo](https://www.npmjs.com/package/expo)]. Совместима ли именно эта пара, сверить по документации Expo (не проверено). Так сохраняется опыт React из BATR, и на RN уже есть открытые приложения-образцы (Bayaan, Open Mushaf). На Flutter готовых библиотек Корана больше (`quran_library`, MIT), но придётся уйти от React.
5. **Время намаза:** официальный API ДУМК, после письменного разрешения, плюс `adhan` (MIT) как резерв без сети. Хиджра — `hijridate` (MIT) с подменой дат праздников по ДУМК. Подбирать углы самим не нужно, если ДУМК даст разрешение.
6. **Учебный движок — FSRS:** `ts-fsrs` 6.0.0 и `py-fsrs` 6.3.3 (MIT), оптимизатор `fsrs-rs` (BSD-3). Геймификацию и серию дней (стрик) делаем сами: зрелых библиотек нет, задача простая.
7. **ИИ.**
   - Объяснения: шаблоны + LLM для формулировки, без аудио.
   - Вопросы и ответы: Claude Citations + pgvector + полнотекстовый поиск Postgres; эмбеддинги `bge-m3` или `multilingual-e5-large` (MIT).
   - Фикх и фетвы не делаем: ведём пользователя в **Imam AI** ДУМК.
   - Открытых датасетов «одобренных ответов» ханафитско-матуридитской линии нет.
8. **Обвязка приложения:**
   - запись PCM 16 кГц — `react-native-audio-api` (MIT);
   - воспроизведение — `expo-audio`;
   - пуши — `expo-notifications`;
   - сбои — Sentry SDK → свой GlitchTip (MIT);
   - аналитика — свой PostHog (ядро MIT) или Aptabase.
   - **Нельзя:** Firebase Analytics, AdMob и рекламный ID — этого требует QML.
9. **Главное лицензионное решение.** QML распространяется на «Covered Product» — продукт целиком. Поэтому AI Ustaz должен быть **отдельным приложением**, а не разделом супер-приложения batr.kz. Иначе запрет рекламы и обязательное ИИ-предупреждение распространятся на всё супер-приложение. Из batr.kz — только ссылка.
10. **Что делаем сами, потому что готового нет:**
    - курс по методике «Муаллим сани» на казахском и русском;
    - эталонные записи;
    - эталонная фонетика для не-коранических слогов;
    - каталог «ошибка → объяснение»;
    - тестовый набор на наших учениках;
    - интеграция и RN-обёртки;
    - логика «слушателя» и кабинет устаза;
    - переводы.

    Дообучение моделей — только если замер на тестовом наборе покажет, что готовые не справляются.

### 1.2. Как запустить muaalem у себя [факт, если не указано иное]

> **Пометка 18.11.2026 (проверено по пакету 0.3.0).** Готовый engine не даёт того, что нужно проверке: `engine/serve.py` → `encode_response` отдаёт только `{"phonemes": строка}` (жадный CTC); `decode_request` дополняет каждый вход до 15 с (`padding="max_length"`); `engine/main.py` вызывает `server.run(port=…)` без host, то есть порт открыт на всех адресах. Вероятности фонем и сифатов даёт только Python API (`inference.py`, класс `Muaalem`). **Решение:** свой речевой сервис (FastAPI + батчинг, порт 8032) загружает модель из `quran-muaalem` 0.3.0 как библиотеку и отдаёт вероятности и покадровые логиты; пакет не меняем, QML соблюдаем. Процессы `engine` и `app` в проде не используем. Ниже — справка о пакете.

По README и метаданным пакета ([PyPI](https://pypi.org/project/quran-muaalem/), [GitHub](https://github.com/obadx/quran-muaalem)):

- **Установка.** `uv add quran-muaalem[engine]`, плюс системные `ffmpeg` и `libsndfile`.
  - Экстра `engine`: `fastapi ≥0.116`, `litserve ≥0.2.17` (Apache-2.0, 0.2.19 от 09.09.2026 — [PyPI](https://pypi.org/project/litserve/)), `uvicorn`, `pydantic-settings`, `httpx`, `python-multipart`.
  - Экстра `ui` — Gradio-демо.
- **Два процесса.**
  - `quran-muaalem-engine` (порт 8000): модель, батчинг до 128, ожидание батча 0,4 с, ускоритель `cuda | cpu | mps`.
  - Приложение (порт 8001): поиск по Корану, фонетизация, анализ ошибок; параметр `error_ratio = 0,1`; число процессов — по `cpu_count // 2`.
- **Вход.** Моно 16 кГц. Python API принимает эталон `quran_phonetizer(..., remove_space=True)` и отдаёт фонемы с вероятностями и сифаты. По умолчанию `dtype = bfloat16`: на этой точности модель обучалась.
- **Выход `/correct-recitation`.** Пример из README для «الٓمٓ»:
  - место чтения: сура, аят, слово, буква;
  - `predicted_phonemes` / `reference_phonemes`;
  - список `errors` с полями `uthmani_pos`, `error_type` (`tajweed` / `normal` / `tashkeel`), `speech_error_type` (`insert` / `delete` / `replace`), `expected_len` / `predicted_len`, `ref_tajweed_rules` (название ar/en, `golden_len`);
  - в примере: «мадд лязим: 6 ожидалось, 2 прочитано».

  Это почти готовая «где и что» для объяснения. Нам остаётся шаблон на казахском и русском: «Здесь мадд лязим: тяните 6 харакатов, вы тянули 2».
- **Какие правила анализ ошибок называет явно.**
  - Калькаля (сравнение `match`).
  - Мадды (сравнение `count`): табии 2, мунфасиль 4, муттасиль 4, муттасиль при вакфе 4, лязим 6, арид 4, лин 4.
  - Остальное — гунна, ихфа, идгамы, тафхим — приходит как расхождение фонем или сифатов, без имени правила. **Имя правила для объяснения берём из `quranic-phonemizer` по той же букве** [оценка].
  - Эталонные длины задаются `MoshafAttributes`: их нужно привести к политике чтения, утверждённой устазами (документ 03, 1.6).
- **ONNX.** Готового экспорта нет. Конвертировать можно (`optimum`, `torch.onnx`), но конвертация считается «Model Derivative», и производная остаётся под QML [факт: определение в QML 1.4].
- **Задержка и железо** [оценка, не замерено]:
  - на GPU уровня L4/A10 один аят 5–15 с обрабатывается за десятки–сотни миллисекунд;
  - к этому добавляется до 0,4 с ожидания батча в LitServe (настраивается);
  - на CPU — секунды на аят, годится только для разработки.

  Цель для продукта №1 — ответ за 1–3 с после конца аята (документ 02, 5.2). Замер — в фазе 0.

### 3.3. GPL/AGPL и магазины приложений

- **[факт]** FSF считает условия App Store несовместимыми с GPL: они ограничивают пользователя. В 2010 году так ушли из магазина GNU Go, а в январе 2011 Apple удалила VLC после жалобы разработчика VLC ([Engadget](https://www.engadget.com/2011-01-09-the-gpl-the-app-store-and-you.html), [TechSpot](https://www.techspot.com/news/41908-apple-removes-vlc-app-from-app-store-gpl-to-blame.html), [vlc-devel](https://mailman.videolan.org/pipermail/vlc-devel/2010-October/076876.html)).
- **[оценка]**
  - GPL-код в iOS-приложении — риск жалобы любого правообладателя.
  - В Google Play GPL возможна, но тогда **всё наше приложение** должно стать GPL с открытым исходным кодом.
  - AGPL требует того же; для сервера — ещё и открыть изменения.
  - Вывод: GPL/AGPL-код в приложение не копируем. Идеи и архитектуру — можно.
- LGPL в мобильном приложении (статическая сборка iOS) тоже проблемна. Берём MIT/Apache-аналоги (`adhan` вместо `adhan.py`/`praytimes`).
- **Исключение.** Если владелец решит открыть приложение под AGPL (бесплатное, «ради Аллаха»), можно будет брать Bayaan. Но и тогда вопрос с App Store не снимается: нужны согласия всех авторов. Не рекомендуем.

### 5.2. Как совпасть с официальным расписанием ДУМК [оценка]

1. **Основной путь.**
   - Письмо в ДУМК: разрешение на использование API в AI Ustaz с атрибуцией.
   - Сервер раз в год (и при изменениях) скачивает таблицы по каждому населённому пункту и хранит их в РК.
   - Приложение получает таблицу своего пункта на год вперёд и работает офлайн.
2. **Резерв, если ДУМК не разрешит или API недоступен.**
   - Подобрать параметры `adhan`: углы фаджра и иши, ханафитский аср, поправки по минутам для каждого намаза.
   - Подбор вести по годовым таблицам ДУМК для 20–30 городов.
   - Автотест в CI: расхождение не больше 1 минуты (документ 08, 6.1).
3. **Узбекистан, Кыргызстан, Россия.** Пресеты по муфтиятам — только после подтверждения у муфтията. Для РФ есть официальные таблицы региональных ДУМ (см. `noor-times`).
4. **Будильник азана.**
   - Android: точные будильники требуют `SCHEDULE_EXACT_ALARM` или `USE_EXACT_ALARM`. Политика Google Play для `USE_EXACT_ALARM` ограничена приложениями «будильник/календарь»; допускаются ли приложения намаза — не подтверждено официальным источником (не проверено). Закладываем `SCHEDULE_EXACT_ALARM` с запросом у пользователя.
   - iOS: не больше 64 запланированных локальных уведомлений, звук до 30 с (документ 08). Планируем на 7–10 дней вперёд и обновляем при каждом запуске.

## 7. ИИ-объяснение ошибок и вопросы-ответы

### 7.1. Объяснение ошибок (продукт №1 и №2)

- **Готового объяснятеля на казахском и русском нет.** muaalem отдаёт названия правил на арабском и английском и умеет печатать объяснение в терминал (`quran_muaalem.explain`).
- **Схема [оценка]:**
  1. JSON ошибок muaalem.
  2. Правило по букве из `quranic-phonemizer`.
  3. Наш каталог «правило × тип ошибки → шаблон kk/ru + пример + аудио» (пишет устаз).
  4. По желанию — LLM перефразирует под уровень ученика, но **не придумывает правил и не слушает аудио** (документ 02).
- **LLM:** BATR уже работает с Anthropic и OpenAI. По справочнику Claude API (кэш 03.11.2026) самая дешёвая модель — Claude Haiku 5.5: $0,10 / $0,50 за 1 млн токенов на вход и выход. Перефразирование одного замечания стоит доли цента [оценка]. В LLM уходит только структурированный список ошибок, без аудио и без персональных данных.

## 12. Риски

| Риск | Вероятность / влияние | Мера |
|---|---|---|
| Ядро таджвида держится на одном авторе (obadx); лицензию уже меняли MIT → QML | Средняя / высокое | Зафиксировать версию и веса у себя (Apache-основа это позволяет); следить за релизами; при смене условий — остаться на текущей версии: прошлые выдачи лицензии не отзываются (не проверено юристом) |
| QML распространится на супер-приложение batr.kz | Высокая, если встроить / высокое | Отдельное приложение и сервис; из batr.kz только ссылка |
| NPL закроет путь к платным функциям (кабинет устаза, B2B) | Средняя / среднее | Платные функции не строить на моделях Quran Lab; держать HisnLabs-путь как основной |
| Привязка к Quran Lab: ключ, CDN, удаление модели при отзыве ключа | Средняя / высокое | Не делать TajweedFormer единственным движком; резерв — HisnLabs или muaalem на сервере |

| Готовые модели плохо работают на наших L1, детях и женщинах | Высокая / высокое | Тестовый набор v0 до любого решения; релизные пороги (документ 02) |
| ДУМК не разрешит API расписания | Низкая–средняя / среднее | Калибровка `adhan` по таблицам (5.2) |
| Отрисовка арабского с цветами ломает лигатуры | Средняя / среднее | Skia-рендер; проверка на 10 популярных в РК телефонах |
| Неверно понятые лицензии (QML 2.2 «шариат», NPL «оценённая модель», дистилляция) | Средняя / высокое | Заключение юриста РК до релиза (документ 03, чек-лист 10) |
| Политики магазинов (точные будильники, разрешения на запись, детская аудитория) | Средняя / среднее | Сверить с официальной политикой Google Play и App Store перед публикацией |

## 13. Вопросы, которые решает владелец

1. **Отдельное приложение.** Подтверждаете, что AI Ustaz живёт отдельно от супер-приложения batr.kz, а из batr.kz к нему ведёт только ссылка? Это требование QML.
2. **NPL-1.2 (Quran Lab).** Готовы ли навсегда держать функции на моделях Quran Lab бесплатными? Включая будущий кабинет устаза и B2B для медресе, если они будут на этих моделях. Если нет — строим только на HisnLabs и muaalem.
3. **Фреймворк.** React Native + Expo (рекомендуется) или Flutter?
4. **API ДУМК.** Отправляем официальное письмо о расписании намаза вместе с меморандумом о курсе таджвида (документ 03, чек-лист 10)?
5. **Шрифт мусхафа.** DigitalKhatt (OFL, рекомендуется) или KFGQPC/QCF через QF?
6. **Аналитика.** Свой PostHog (больше возможностей) или Aptabase (минимум данных)? Оба без рекламы и в РК.
7. **Псевдоразметка.** Разрешаем ли обучать наши будущие модели на выходах muaalem? Это серая зона QML: производная останется под QML.
